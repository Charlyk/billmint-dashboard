<task type="auto">
  <name>Task 1: Create centralized analytics event tracking module</name>
  <files>src/lib/analytics/events.ts</files>
  <action>
Create `src/lib/analytics/events.ts` with the following structure:

1. Import `posthog` from `posthog-js` and `isProduction` from `./posthog`.

2. Create a `track()` helper function that:
   - Returns early if `typeof window === 'undefined'` (server-side safety — posthog-js is client-only)
   - Returns early if `!isProduction` (environment gating from Phase 3)
   - Wraps `posthog.capture(eventName, properties)` in try-catch
   - Catches silently (never break app for analytics). Do NOT log errors to console — the Axiom logger is server-side only and console.error would be noise in dev.

3. Export `const analytics` object with typed methods for ALL 27 events across 5 requirement groups. Use the exact event names and property types from the research:

   **Timer lifecycle (EVT-01) — 5 events:**
   - `timerStarted(props: { project_id?: string | null; is_billable: boolean })`
   - `timerPaused(props: { duration_seconds: number })`
   - `timerResumed(props: { duration_seconds: number })`
   - `timerStopped(props: { timer_id?: string; duration_seconds: number; project_id?: string | null; is_billable: boolean; description_length: number })`
   - `timerDiscarded(props: { duration_seconds: number })`

   **Invoice lifecycle (EVT-02) — 5 events:**
   - `invoiceCreated(props: { invoice_id: string; client_id: string; amount: number; currency: string; line_item_count: number })`
   - `invoiceSent(props: { invoice_id: string; amount: number; currency: string })`
   - `invoiceViewed(props: { invoice_id: string })`
   - `invoiceMarkedPaid(props: { invoice_id: string; amount: number; currency: string })`
   - `invoiceVoided(props: { invoice_id: string })`

   **Billing events (EVT-03) — 4 events:**
   - `checkoutStarted(props: { tier: 'pro' | 'business' })`
   - `subscriptionActivated(props: { tier: 'pro' | 'business' })`
   - `planChanged(props: { from_tier: string; to_tier: string })`
   - `subscriptionCancelled(props: { tier: string })`

   **CRUD events (EVT-04) — 9 events:**
   - `clientCreated()` (no props needed — anonymous tracking, no PII)
   - `clientEdited(props: { client_id: string })`
   - `clientDeleted(props: { client_id: string })`
   - `projectCreated(props: { project_id: string; client_id?: string | null })`
   - `projectEdited(props: { project_id: string })`
   - `projectArchived(props: { project_id: string })`
   - `timeEntryCreated(props: { entry_id: string; duration_seconds: number; is_billable: boolean })`
   - `timeEntryEdited(props: { entry_id: string })`
   - `timeEntryDeleted(props: { entry_id: string })`

   **Funnel-ready events (EVT-05) — 4 events:**
   - `signupCompleted()` (no props)
   - `firstProjectCreated()` (no props)
   - `firstTimerStarted()` (no props)
   - `firstInvoiceSent()` (no props)

Each method calls `track('event_name', props)` with the appropriate snake_case event name. Event names follow `object_action` format with past tense (e.g., `timer_started`, `invoice_created`).

Add a JSDoc comment at the top of the file documenting:
- Privacy rules: IDs only, counts/lengths not content, never PII
- Environment: Production-only via isProduction check
- Browser-only: typeof window check prevents server-side calls

Do NOT use Zod validation on event properties — TypeScript types are sufficient and avoid runtime overhead. Do NOT use enums for event names — string literals in the track() calls are more readable and greppable.

  <action>
Add timer lifecycle event tracking to `src/contexts/timer-context.tsx`:

1. Add import at top: `import { analytics } from '@/lib/analytics/events'`

2. In `startTimer` callback — after the successful `timerApi.startTimer()` call returns (inside the try block, after `setTimer` with server response):
   ```
   analytics.timerStarted({
     project_id: serverTimer.project_id,
     is_billable: serverTimer.is_billable,
   })
   ```
   Track AFTER server confirms success (not in the optimistic update before the API call).

3. In `stopTimer` callback — after `timerApi.stopTimer()` succeeds (inside the try block, before the toast):
   ```
   analytics.timerStopped({
     duration_seconds: savedDuration,
     project_id: prevTimer.projectId,
     is_billable: prevTimer.isBillable,
     description_length: prevTimer.description.length,
   })
   ```
   Use `prevTimer` (saved before optimistic reset) and `savedDuration` (saved before reset) for the properties.

4. In `pauseTimer` callback — after `timerApi.pauseTimer()` succeeds (inside the try block, after the await):
   ```
   analytics.timerPaused({
     duration_seconds: currentDisplayTime,
   })
   ```
   Use `currentDisplayTime` which was captured before the API call.

5. In `resumeTimer` callback — after `timerApi.resumeTimer()` succeeds (inside the try block, after the await):
   ```
   analytics.timerResumed({
     duration_seconds: currentElapsed,
   })
   ```
   Use `currentElapsed` (`timer.elapsedSeconds`) which was captured before the API call.

6. In `discardTimer` callback — after `timerApi.discardTimer()` succeeds (inside the try block, before the toast):
   ```
   analytics.timerDiscarded({
     duration_seconds: displayTime,
   })
   ```
   Capture `displayTime` BEFORE the optimistic reset. Note: `displayTime` is already available in the callback scope from the component state. But the optimistic update resets it to 0. So save it at the top of the function: `const savedDisplayTime = displayTime` and use that.

   Wait — looking at the code more carefully: `discardTimer` already saves `prevTimer` which has `elapsedSeconds`. Use `prevTimer.elapsedSeconds` OR capture `displayTime` at the start of the function. The `displayTime` state value is captured at function call time (before any setState), so it's safe to use directly inside the try block.

Key rules:
- Track AFTER successful API response (inside try block, after await)
- Never track in the error path (catch blocks)
- Never await analytics calls (they're fire-and-forget via posthog-js batching)
- Use data available in scope (prevTimer, savedDuration, currentDisplayTime, etc.) — do NOT make additional API calls for analytics properties
- Add `displayTime` to the dependency array of `discardTimer` useCallback if not already there (it already is — verify)

Do NOT add `analytics` to any useCallback dependency arrays — it's a module-level constant object, not a React state/prop.
