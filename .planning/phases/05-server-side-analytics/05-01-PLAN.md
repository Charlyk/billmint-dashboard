<task type="auto">
  <name>Task 1: Install posthog-node and create server-side PostHog client</name>
  <files>package.json, src/lib/analytics/posthog-server.ts</files>
  <action>
1. Install posthog-node: `npm install posthog-node`

2. Create `src/lib/analytics/posthog-server.ts` with:
   - Import `PostHog` from `posthog-node`
   - Import `isProduction`, `POSTHOG_KEY`, `POSTHOG_HOST` from `./posthog` (reuse existing config)
   - Lazy-initialized singleton: `let client: PostHog | null = null`
   - `getPostHogServer()` function that returns client or null:
     - Returns null if `!isProduction` or `!POSTHOG_KEY`
     - Creates `new PostHog(POSTHOG_KEY, { host: POSTHOG_HOST, flushAt: 1, flushInterval: 0 })` on first call
     - flushAt: 1 and flushInterval: 0 because webhook events are low-volume and must not be lost
   - Register graceful shutdown: `process.on('SIGTERM', ...)` and `process.on('SIGINT', ...)` that call `client.shutdown()` — only register once (use a `shutdownRegistered` flag)
   - Export `serverAnalytics` object with typed methods matching the 3 billing events from events.ts:
     - `subscriptionActivated(props: { userId: string; tier: 'pro' | 'business' })` — calls `client.capture({ distinctId: props.userId, event: 'subscription_activated', properties: { tier: props.tier } })`
     - `planChanged(props: { userId: string; from_tier: string; to_tier: string })` — calls `client.capture({ distinctId: props.userId, event: 'plan_changed', properties: { from_tier, to_tier } })`
     - `subscriptionCancelled(props: { userId: string; tier: string })` — calls `client.capture({ distinctId: props.userId, event: 'subscription_cancelled', properties: { tier: props.tier } })`
   - Each method: get client via `getPostHogServer()`, if null return silently (same pattern as client-side events.ts), wrap in try/catch with silent catch (never break webhooks for analytics)
   - Use `userId` as `distinctId` — this is the Supabase user UUID, not PII (matches project's anonymous-only constraint since PostHog is configured with `person_profiles: 'identified_only'` which means capture-only calls don't create person profiles)

Note: Do NOT use `person_profiles` in posthog-node constructor — that's a posthog-js option. posthog-node captures are anonymous by default when no `$set` properties are included.
  </action>

- `npx tsc --noEmit` passes (no type errors)

- File exports `serverAnalytics` with 3 methods
  </verify>

<task type="auto">
  <name>Task 2: Add server-side billing event tracking to Stripe webhook handler</name>
  <files>src/lib/services/billing.service.ts</files>
  <action>
1. Add import at top of billing.service.ts: `import { serverAnalytics } from '@/lib/analytics/posthog-server'`

2. In `handleWebhook()`, add tracking calls AFTER successful database operations (same pattern as client-side: track after success, never before):

   **checkout.session.completed** (SSA-01 — subscription_activated):
   After the successful `supabase.rpc('handle_stripe_webhook', ...)` call and BEFORE the `log.info('Webhook processed', ...)`:
   ```typescript
   serverAnalytics.subscriptionActivated({ userId, tier })
   ```

   **customer.subscription.updated** (SSA-02 — plan_changed):
   This case currently only handles `canceled` or `unpaid` status (downgrade to free). After the successful RPC call:
   ```typescript
   serverAnalytics.planChanged({ userId: customerId, from_tier: subscription.status === 'canceled' ? 'paid' : 'paid', to_tier: 'free' })
   ```
   Note: We use customerId as distinctId here because userId is not available in this webhook event (Stripe sends customer ID, not our user ID). The RPC already handles the mapping. Use `customerId` as distinctId — PostHog will group by this identifier. Document this limitation with a comment.

   **customer.subscription.deleted** (SSA-03 — subscription_cancelled):
   After the successful RPC call:
   ```typescript
   serverAnalytics.subscriptionCancelled({ userId: customerId, tier: 'free' })
   ```
   Same customerId note applies. The subscription is fully deleted so tier is 'free'.

3. Important: Do NOT add tracking to `invoice.payment_failed` — that's not in requirements and is a different event type.
  </action>
